§ 02 · Pipeline

AI 驱动的测试全流程流水线

测试不是线性流程，而是闭环。每轮经验沉淀进知识库，下一轮更精准。

P0
需求评审 — 三剑客对抗
产品专家/架构师/测试专家三个 LLM Agent 独立剖析 → 红蓝对抗互质询 → 盲区清单 + 风险定级
🛑 GATE-0：无 P0 级歧义
P1
测试用例生成 V1
十维度框架（功能/输入/边界/规则/状态/异常/幂等/容错/安全/性能）+ 六项硬门禁 + 需求追溯矩阵
🛑 GATE-1：6 项自检全部 PASS
P3
Code Review — 理解代码实现
不只找 Bug，更理解代码实际实现了什么 → 输出风险地图（隐含分支/未文档化接口/安全风险）
⚠️ GATE-3：P0/P1 必须校准
★P4
需求 × 代码交叉验证 — 全流水线 ROI 最高
三剑客以需求反查代码分支、以代码 diff 反推用例缺口 → 产出 V2 用例：增补隐含需求 + 剔除冗余 → 精准化测试（改哪测哪）
🟢 GATE-4：三方映射表完整
P6
自动化测试 & 结果分析
脚本自动生成 + 失败自修复（≤3 次）→ 决策树严格区分「脚本 Bug」vs「产品 Bug」vs「API 变更」vs「环境问题」
🟢 GATE-6：脚本无语法错误
P10
测试报告
金字塔原理——头部决策表 3 秒呈现 Go / No-Go；数据优于形容词，趋势优于快照
🏁 IEEE 829 标准输出
闭环：线上 bug 回流 → 更新测试分级 → 加严门禁阈值 → 下一轮自动更准——循环不是单行道。

§ 04 · Cross Validation ★

需求 × 代码交叉验证（Phase 4 ★）

大多数测试覆盖不足的根源：只从需求生成用例，不回头看代码实际做了什么。

场景只看需求交叉验证后（AI 三剑客）
分页功能只测正常分页代码还实现了游标分页 → 补充测试
并发处理不测并发发现代码用了分布式锁 → 补充并发用例
内部接口暴露完全不知情发现未文档化的内部接口 → 堵住安全漏洞
精准化测试的种子在这里种下：代码 diff → 变更影响集 → 只跑受影响的用例子集。改哪测哪——改一行代码圈 8 条用例，不是全量 250 条。
§ 05 · Coverage Proof

用例覆盖率的三层证据链

1
事前 · 生成端约束
十维度框架每维 ≥5 条硬门禁、需求原子化追溯矩阵（无孤儿需求点 = 需求覆盖 100% 可查表）
2
事中 · 对抗补强
三剑客红蓝对抗专找遗漏、历史缺陷反例库注入、Code Diff 反查用例缺口
3
事后 · 量化验证
代码覆盖率（行/分支）、变异测试杀死率（比覆盖率更硬的有效性指标）、缺陷逃逸率复盘
一句话答案：AI 拉广度、人核深度、缺陷史补盲区——三者合并才是真覆盖。实测 30% → 100%。

§ 07 · Anti-Patterns

常见陷阱与反模式

陷阱 1：跳过需求评审直接生成用例——导致边界和异常全漏。
Phase 0 是硬门禁，输入必须是澄清后的需求。
陷阱 2：自动化失败直接报 Bug——一半是脚本自身问题。
先过 Phase 7 决策树排查脚本 Bug vs 产品 Bug。
陷阱 3：把 AI 输出当事实
语义类结论裁判模型复核；事实类结论程序断言验证——两条通道独立。
§ 08 · Loop Engineering

与 Loop Engineering 的关系

这套方法论本质上是一个测试驱动的 Loop。你不应该再手动提示 AI，而是设计让 AI 自己持续运行的循环：

Intent 目标→ Context 知识库→ Action 生成执行→ Observe 结果分析→ Adjust 修正用例→ Loop ↻
9 个开源 Skill 就是这个 Loop 的具体实现——每个 Skill 负责 Loop 的一环，组装起来就是完整的自驱动测试流水线。
