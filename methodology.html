需求驱动、代码交叉验证、证据闭环的工程化流水线。

Prologue / Why This Methodology

为什么需要这套方法论

团队拿到 Skill 后反馈两个极端：

痛点根因
覆盖不足 需求文档不够细致，AI 只覆盖了显式需求，隐含分支和边界条件全漏
用例冗余 AI 不加判断地穷举组合，生成的用例人肉排查比手写还累

这两个问题的本质是同一个：缺少从需求到代码到测试的闭环验证。

测试用例不是一次性产物，它在需求评审时初生，在代码交叉验证时修正，在自动化执行时闭环。每一步都有质量门禁，每一步都有证据。

00 / Knowledge Base

构建知识库 — AI 的记忆体系基础

没有 Memory，AI 每次都从零开始。有了知识库，AI 才懂你的项目、你的业务、你的历史踩坑。事实像档案进仓库，例子像故事变测试数据，规矩像手册变 Skill 文件。

三层架构

层级内容存储作用
长期记忆方法论、测试策略、经验笔记Obsidian / Git跨项目知识沉淀
项目记忆PRD、接口文档、源代码、Git 历史项目仓库当前项目上下文
测试资产历史用例、脚本、Bug 记录test_cases/基线参考、模式匹配

知识库如何赋能每个 Phase

Phase没有知识库有知识库
0 需求评审每个歧义都要问 PM知识库自动回答 40-70% 的问题
1 用例生成从零生成，覆盖取决于 PRD历史用例作为基线，只增量补充
4 交叉验证人肉逐行比对AI 自动比对，产出三方映射表
7 结果分析从头分析失败原因历史 Bug 模式匹配，快速定位
10 测试报告只有当前数据可与历史趋势对比
🔴
GATE-PRE：知识库是所有 Phase 的前置依赖。没有知识库的 AI 测试 = 每次都从零开始的实习生。

01 / Phase 0

需求评审 — 把模糊变成可测

模糊的需求流进代码，模糊的需求就会流进测试用例。上游不澄清，下游全返工。

两种评审方式

方式一：轻量评审 需求 ≤ 3 页

直接使用 requirement-review skill。它会先扫描已有代码库和文档，自动回答 40-70% 的问题（Phase 0 知识库交叉验证），再做三视角分析 + 红蓝对抗，最后输出三级分类结论。

方式二：深度评审 复杂需求 / 新业务

先用 three-musketeers 做全方位深度分析（产品/架构/QA 三视角 + 红蓝对抗），再用 requirement-review 做知识库交叉验证补全。

关键产出

产出物用途
需求澄清清单Phase 1 用例生成的输入
风险标注表（🔴🟡🟢）决定测试投入分配
隐含需求清单Phase 4 交叉验证的基准
QA 验收清单最终测试报告的判定依据
🔴
GATE-0：所有 P0 级歧义必须有明确结论（PM 确认或知识库佐证），不能带「待定」进入 Phase 1。
02 / Phase 1

测试用例生成 V1 — 从需求到覆盖

使用 test-case-generator skill，输入澄清后的需求（不是原始 PRD）。Skill 内置 10 个测试维度，每个维度强制最少 5 条用例。

10 维度覆盖矩阵

维度关注什么典型场景
功能正确性主流程走通正常下单、正常支付
输入验证参数校验完备空值、超长、特殊字符
边界值临界点行为0、1、最大值、最大值+1
业务规则复杂条件组合优惠券叠加规则
状态转换状态机覆盖订单状态流转
异常处理错误场景恢复网络超时、支付失败重试
并发/幂等重复请求行为重复提交、并发扣减
容错性部分依赖失效缓存宕机、第三方不可用
安全性越权和注入水平越权、SQL 注入
性能响应时间基准单接口 P99 < 200ms

03 / Phase 3

Code Review — 不只是找 Bug，是理解代码做了什么

使用 code-review skill 对提测代码进行审查。

Code Review 在测试流程中的价值，不只是找代码 Bug —— 它的真正价值是理解代码实际实现了什么，为下一步的交叉验证提供事实基础。

维度传统认知方法论认知
目的找代码缺陷理解代码实际实现了什么
产出Bug 列表风险地图 + 实现偏差清单
下游开发修复反哺测试用例（Phase 4）

五步审查流程

  • 上下文理解：读全部源码、PRD、配置、Git 历史
  • 三视角分析：业务正确性 / 架构与并发 / 健壮性与可测性
  • 定级：P0 阻塞 → P3 信息
  • 定级校准：对每个 P0/P1 做「魔鬼代言人」质询，防止虚高
  • 决策：✅ 可发布 / ⚠️ 修 P1 后可发布 / ❌ 阻塞
🟡
GATE-3：Code Review 不得有未校准的 P0/P1 发现。每个高级别问题必须经过校准质询。
04 / Phase 4 ★ Core

需求 × 代码交叉验证 — 全流水线 ROI 最高的一步

大多数测试覆盖不足的问题，根源都在这里：只从需求生成用例，不回头看代码实际做了什么。

为什么要交叉验证

场景只看需求交叉验证后
需求说「支持分页」只测正常分页代码还实现了游标分页 → 补充测试
需求没提并发不测并发代码里用了分布式锁 → 补充测试
需求说「返回列表」只测有数据空列表返回 null → 发现 Bug
代码多了个内部接口不知道接口文档没写但已暴露 → 安全风险

图 3：AI 交叉验证三剑客流程 — 三视角扫描 + 红蓝对抗 → 交叉验证矩阵 → 用例 V2

人工 vs AI — 为什么交给 AI？

维度纯人工AI 三剑客
效率逐行比对 1-2 天自动扫描 30 分钟
覆盖容易疲劳遗漏三视角正交，不重不漏
可重复每次结果不同可固化、可审计

失败分类决策树 Phase 7

测试失败 │ ├─ 批量失败 ──→ 环境问题 → 修复环境后重跑 │ └─ 单个失败 │ ├─ 断言有误 ──────────→ 脚本Bug → 修脚本重跑 │ ├─ 参数有误 ──────────→ 脚本Bug → 修脚本重跑 │ ├─ 文档与实际不一致 ──→ API变更 → 更新基准重跑 │ └─ 文档与实际一致 ────→ ✅ 确认产品Bug → 进入 Phase 8

每个失败先过决策树：脚本 Bug → 修脚本；API 变更 → 更新基准；确认产品 Bug → 才报。 这是建立开发信任的关键。

06 / Phase 8-9

缺陷反馈 & 回归测试

缺陷反馈文档 Phase 8

开发最烦的反馈：「这个接口有问题」。
开发最喜欢的反馈：「这个接口在 X 参数下返回 Y，但应该是 Z，这是代码位置和复现步骤」。

反馈文档四要素
  • 完整请求参数 + 实际响应 + 预期响应 — 开发不需要猜
  • 代码位置定位 — 文件、方法、行号
  • 测试数据 — 开发能立刻复现的账号和数据
  • Code Review 关联 — 如果 CR 已标注，引用编号

回归测试 Phase 9

回归测试采用基线对比策略（借鉴 Harness Engineering 核心方法论）：

对比结果含义
Pass → Fail回归 修复引入了新问题
Fail → Pass修复成功
Fail → Fail修复无效
Pass → Pass未受影响
🔴
GATE-9：回归测试不得引入新的 P0/P1 失败。如有，打回修复。

测试报告生成

使用 test-report-generator skill，遵循 Minto 金字塔原理：结论先行，细节后补。

章节内容给谁看
头部决策表Go / No-Go + 核心数字所有人（3 秒看完）

执行结果用例统计、通过率、趋势测试 + 开发
缺陷分析分类统计、严重分布、遗留开发 + PM
风险评估遗留风险、建议决策者

原则✅ 正确❌ 错误

08 / Anti-Patterns

常见陷阱与反模式

陷阱 1 跳过需求评审，直接生成用例

症状：用例覆盖主流程，边界和异常全漏。
对策：Phase 0 是硬门禁。输入给 test-case-generator 的必须是澄清后的需求。

陷阱 2 用例生成后不再修正

症状：用例和实际代码脱节。
对策：Phase 4 交叉验证是 ROI 最高的环节，不可跳过。

陷阱 3 盲目追求用例数量

症状：500 条用例，300 条是冗余。
对策：用例数量服从覆盖度，不服从"多就是好"。

陷阱 4 自动化脚本失败就报 Bug

症状：报了一堆 Bug，一半是脚本自己的问题。
对策：每个失败先过 Phase 7 决策树。先排查脚本，确认后才报产品 Bug。

陷阱 5 没有基线对比

症状：回归测试说「通过了」，但没人知道上轮什么状态。
对策：每次回归前记录基线，回归后对比增量。堵死"历史遗留"借口。

陷阱 6 Code Review 和测试割裂

症状：Code Review 发现了风险，但测试用例没有针对性加强。
对策：Code Review 的每个 P0/P1 发现都要在 Phase 4 转化为测试用例。

09 / Summary

如果只记三条

  1. 需求不澄清就生成用例，等于在地基没打好的时候盖楼。 Phase 0 是硬门禁，输入必须是澄清后的需求，不是原始 PRD。
  2. 不看代码就测，等于闭着眼睛打靶。 Phase 4 交叉验证是 ROI 最高的环节 — 需求 × 代码矩阵确保隐含分支不遗漏。
  3. 自动化失败不等于 Bug，先排查脚本再报问题。 Phase 7 决策树是建立开发信任的基础。

测试的本质不是「执行用例」，而是「证明需求被正确实现」。这套方法论把测试从一次性活动变成一个闭环：需求评审定义「什么是对的」，测试用例描述「怎么证明它对了」，代码交叉验证发现「实际做了什么」，自动化执行「快速证明」，结果分析「判断对错」，测试报告「给出结论」。

每一步都有证据。每一步都可追溯。

方法论不是一次定稿的，它是被每一轮测试的痛点驱动的。
先跑，撞墙了再补对应环节。

10 / Loop Engineering

与 Loop Engineering 的关系

这套测试方法论本质上就是一个测试驱动的 Loop — 你不应该再手动提示 AI，你应该设计让 AI 自己持续运行的 Loop。

Loop Engineering 要素测试方法论映射
自动触发器每次提测触发全流程；CI 失败触发回归
技能文件（Skills）每个 Skill 就是一个 SKILL.md，固化为可复用资产
子 Agent（Maker-Checker）三剑客交叉验证 = AI 审 AI
持久记忆知识库（§00）= Loop 的记忆系统
